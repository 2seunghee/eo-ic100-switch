# 동작 원리 — usbhs-logmitm 0.2.1이 바꾸는 것과 UAC 1.0, 그리고 FM 라디오

이 문서는 실기기 디스크립터(`dumps/04e8_a05b_config.bin`, `04e8:a05b`, 345바이트)를 해석한 결과와 실기기 로그(docs/PLAN.md §0)를 근거로 한다.

## 1. 0.2.1이 바꾸는 것 — 2개 필드, 실제로 달라지는 바이트는 3개

| 위치 | 필드 | 원래 값 | 바꾼 값 |
|---|---|---|---|
| OT6 (재생 경로의 출력 단자) | wTerminalType | `0x0402` Headset | `0x0302` Headphones |
| IT1 (마이크 경로의 입력 단자) | wTerminalType | `0x0402` Headset | `0x0201` Microphone |

길이, 엔드포인트, 포맷, 샘플레이트는 그대로다. 이어폰 자체도 바꾸지 않는다. 바꾸는 것은 오디오 모듈(`audio`, 0100000000000014)이 읽어 간 메모리 사본뿐이다.

0.2.0과 0.2.1의 차이:
- 실시간 요청(isoc 배치, 프레임 번호)을 SD 기록을 기다리지 않고 바로 넘긴다. 0.2.0은 fsync한 뒤 넘겨서 배치가 시작 프레임을 놓쳤고, 소리가 나지 않았다.
- 도메인 대답의 EP 객체 번호를 바르게 읽는다(로그에만 영향).

## 2. EO-IC100 디스크립터와 UAC 1.0 비교

결론: **EO-IC100은 UAC 1.0을 어긴 장치가 아니다.** 규격이 허용하는 범위보다 닌텐도 드라이버가 받아들이는 범위가 좁을 뿐이다.

| 항목 | EO-IC100 (a05b) | UAC 1.0 | 스위치 드라이버 |
|---|---|---|---|
| bcdADC | `0x0100` | 1.0 | 통과 |
| 구성 | AC(IF0) + AS 2개(IF1 마이크, IF2 재생) + HID 2개(IF3, IF4) | 정상 | HID는 audio가 보지 않음 |
| 재생 경로 | IT4(USB 스트림 `0x0101`) → FU5 → **OT6 `0x0402`** | Headset(0x04xx 양방향 계열)은 입력·출력 단자 어디에나 쓸 수 있음 | **출력 장치로 등록하지 않음 (H2)** |
| 마이크 경로 | **IT1 `0x0402`** → FU2 → OT3(`0x0101`) | 정상 | 같은 이유로 거부된 것으로 추정 |
| 재생 alt1 | PCM 16비트 2채널, 48·96 kHz, 최대 패킷 384 B | 정상(Type I은 여러 레이트 가능) | 통과. SET_CUR로 48000 설정 |
| 재생 alt2·alt3 | 24비트, 32비트 | 정상 | 무시하고 alt1 사용 |
| 엔드포인트 | isochronous, synchronous(`0x0d`), 1 ms | 정상 | 통과 |
| 마이크 alt1 | 16비트 2채널 48 kHz, 192 B | 정상 | 미확인 |

UAC 1.0 단자 종류(Terminal Types)의 분류:
- `0x02xx`: 입력(Microphone 등)
- `0x03xx`: 출력(Speaker, Headphones 등)
- `0x04xx`: 양방향(Handset, Headset 등)

삼성은 "마이크 달린 헤드셋"이라는 뜻으로 양쪽 단자에 `0x0402`를 넣었다. 윈도우, 안드로이드, 리눅스는 이 값을 받아들인다. 스위치 드라이버는 출력 단자가 `0x03xx`인 장치만 출력 장치로 등록하는 것으로 보인다.

실기기 증거(C-0 로그): audio는 디스크립터를 읽고 AS 인터페이스 2개를 쥐었다. 그다음 아무 요청도 보내지 않았다. 통신 실패가 아니라 분류 단계에서 탈락한 것이다. 바로잡을 곳은 이 두 필드뿐이었다. 96 kHz와 24/32비트 alt는 드라이버가 알아서 걸렀다.

## 3. 동작 원리

1. **단자 종류는 설명용 이름표다.**
   - wTerminalType은 데이터 경로에 관여하지 않는다. 호스트가 장치를 분류하고 연결할 곳을 정할 때만 쓴다.
   - 소리가 오가는 엔드포인트, 포맷, 레이트는 그대로다.
   - 그래서 호스트가 보는 사본만 고치면 된다. 이어폰은 아무것도 모른 채 평소대로 동작한다.
2. **닌텐도 자체 드라이버를 그대로 쓴다.**
   - 바뀌는 것은 판정의 입력뿐이다.
   - 판정을 통과하면 나머지는 닌텐도의 USB 오디오 경로가 한다.
     - SetInterface alt1
     - SET_CUR 48000
     - 1 ms마다 192 B(48샘플 × 2채널 × 2바이트)씩 isochronous 전송, 5개 묶음
   - 그래서 홈 UI, 게임, 홈브루(audout) 소리와 볼륨 UI가 모두 정식처럼 동작한다.
3. **응답이 audio에 닿기 직전에 끼어든다(Atmosphère mitm).**
   - usb:hs를 가로챈다.
   - `mitm.lst`가 있으면 boot2가 audio를 이 mitm이 뜰 때까지 기다리게 한다. 그래서 audio가 부팅 때 여는 첫 세션도 잡힌다.
   - 디스크립터는 두 단계로 audio에 전달된다.
     - CtrlXferAsync(GET_DESCRIPTOR CONFIG): 바이트를 USB 서비스가 audio 메모리에 직접 쓴다.
     - GetCtrlXferReport: "끝났다"는 알림이다.
   - mitm은 이 알림을 돌려주기 직전에 고쳐 쓴다. audio는 해석을 시작하는 순간 이미 고쳐진 값을 본다.
4. **다른 프로세스의 메모리를 디버그 권한으로 고친다.**
   - npdm에 `force_debug`를 넣고 svc 세 개를 쓴다.
     - `svcDebugActiveProcess`로 audio에 붙는다.
     - `svcReadDebugProcessMemory`로 읽는다.
     - `svcWriteDebugProcessMemory`로 쓴 뒤 다시 읽어 확인한다.
   - 길이가 바뀌지 않으므로 audio가 계산해 둔 오프셋과 크기가 어긋나지 않는다.
5. **CMIF 도메인을 해석한다.**
   - audio는 usb:hs를 도메인 세션으로 쓴다.
   - 객체 번호를 따라가야 어느 인터페이스·엔드포인트의 몇 번 명령인지 안다.
   - 이것으로 EO-IC100(VID/PID)의 CONFIG 응답만 골라 고친다.
6. **타이밍 규칙 두 가지(실패에서 배운 것).**
   - 실시간 요청은 지연 없이 넘긴다.
     - isoc 배치에는 시작 프레임(현재 + 13)이 정해져 있다.
     - 0.2.0은 SD 기록 때문에 11~266 ms 늦었다.
   - 원래 응답을 받은 뒤(forward)부터 돌려줄 때(reply)까지는 IPC를 하지 않는다.
     - 원래 응답은 스레드의 TLS(IPC 버퍼)에 있다. 그 사이에 IPC를 하면 그 대답이 이 자리를 덮어쓴다.
     - 0.2.2~0.3.3은 이 사이에 `fopen`을 불렀다. 그래서 audio가 파일 시스템의 대답을 받았고, 이어폰이 인식되지 않았다. 0.3.4에서 고쳤다.

요약: audio가 디스크립터를 해석하기 직전에 양방향 이름표 두 개를 표준 출력·입력 값으로 바꾼다. 재생은 닌텐도 정식 경로가 한다.

## 4. FM 라디오(eofm)는 이어폰의 무엇을 쓰나

EO-IC100에는 USB 오디오 칩(Bestechnic) 안에 FM 수신기("BesFM")가 들어 있다.
- 이 기능은 UAC 규격 밖의 **삼성 전용 벤더 요청**으로 조작한다.
- 프로토콜은 삼성 프레임워크를 디컴파일한 [kjy00302/eo-ic100_radio](https://github.com/kjy00302/eo-ic100_radio)에서 가져왔다.
- 디스크립터에는 FM에 관한 내용이 전혀 없다.

| 무엇 | 어떻게 |
|---|---|
| 명령 통로 | EP0 컨트롤 전송. `bmRequestType 0xC0`(벤더, 장치 대상) |
| SET | `bRequest 0xA1`. wValue = 명령(0 전원, 1 대역, 3 간격, 4 음소거, 5 볼륨, 6 모노, 7·8 탐색 시작·중지, 9 주파수, 10 RDS, 14 녹음) |
| GET | `bRequest 0xA2`. wValue = 명령. 2바이트 응답 |
| QUERY | `bRequest 0xA3`. 12바이트 응답: 탐색 결과(type 0), 맞춤 결과(type 1, 신호 세기 포함), RDS 그룹(type 2) |
| 안테나 | 이어폰 줄 |
| 소리 경로 | 칩이 받은 방송을 **이어폰 안에서 바로** 이어폰 DAC로 보낸다. USB로 소리 데이터가 오가지 않는다 |
| 스위치 쪽 통로 | usb:hs는 쥐고 있는 인터페이스로만 컨트롤 전송을 허락한다. 그래서 eofm은 IF0(AudioControl)을 잡는다 |
| IF0을 쓸 수 있는 이유 | audio는 꽂을 때 디스크립터를 읽느라 잠깐 IF0을 빌린 뒤 놓는다. eofm은 꽂은 지 6초가 지나 IF0이 비면 잡는다 |

그래서 다음이 가능하다.
- 라디오 소리와 스위치 소리(IF2 isoc 재생)가 이어폰 안에서 섞여 함께 들린다.
- `+`로 앱을 나가도 칩이 계속 켜져 있어서 라디오가 계속 나온다.

스피커 출력(포기, `switch/eofm/attic/README.md`):
- 칩을 녹음 모드(`SET 14 = 1`)로 두면 라디오 소리가 USB 마이크(IF1, EP 0x83 isoc IN)로 스위치에 들어온다.
- 그 마이크를 audio와 나눠 쓰려던 두 방법이 모두 audio를 중단시켰다.
  - audin에 잘못된 핸들이 들어감: 2003-0501
  - audio의 목록에서 이어폰을 숨김: Data Abort
- 그래서 이어폰 전용으로 정리했다.

이어폰 리모컨 버튼은 HID(IF3)로 들어온다. 이 인터페이스는 스위치 hid가 쥐고 있다. usbhs-logmitm 0.3.x의 `remote=1`은 hid가 받는 보고를 옆에서 읽는 실험 기능이다(기본 꺼짐, 실기기 미확인).
